# LabSaver Release Process

This document outlines the step-by-step process for publishing a new version of the LabSaver extension to the Chrome Web Store. Following this process ensures that releases are consistent, tested, and safe.

## 1. Pre-Release Checklist

Before starting the release process, ensure the following steps have been completed on the `main` or `feature` branch that is being released.

-   [ ] **Code Freeze**: All new feature development for this release has been merged. Only bug fixes for the current release should be considered.
-   [ ] **Automated Tests**: All automated tests are passing. Run `npm run test:all` to verify.
-   [ ] **Manual Testing**: A thorough manual test of the extension has been completed in a development build (`npm run build:dev`). This includes:
    -   [ ] Successful data export from Function Health.
    -   [ ] Successful data export from Sutter Health.
    -   [ ] Verification of data integrity in the generated Google Sheet.
    -   [ ] No errors in the background or content script consoles.
-   [ ] **Documentation Updated**: All relevant documentation (`README.md`, `ARCHITECTURE.md`, etc.) has been updated to reflect any changes in this release.
-   [ ] **Changelog Updated**: [`CHANGELOG.md`](./CHANGELOG.md) has been updated with a new version entry detailing all changes.

## 2. Version Management

The extension's version number must be updated in two places. We follow [Semantic Versioning](https://semver.org/).

1.  **Update `package.json`**: Increment the `version` field in [`package.json`](package.json).
    ```json
    "version": "2.0.4"
    ```

2.  **Update `config/common.json`**: Increment the `version` field in [`config/common.json`](config/common.json) to match `package.json`. This is the version that will be embedded in the final `manifest.json`.
    ```json
    "version": "2.0.4"
    ```
    **Note**: It is critical that these two version numbers are kept in sync.

## 3. Building for Production

The production build process requires the `config/production.json` file, which contains the official Chrome Web Store OAuth client ID. This file is **not in Git** and must be securely managed.

### Step 1: Prepare the Release Environment
1.  Ensure your local repository is clean and up-to-date with the release branch (e.g., `main`).
    ```bash
    git checkout main
    git pull origin main
    ```
2.  Make sure the `config/production.json` file is present in the `config/` directory. If it is not, you cannot proceed. This file should look like this, with the real production client ID:
    ```json
    {
      "oauth2": {
        "client_id": "YOUR_PRODUCTION_CLIENT_ID.apps.googleusercontent.com"
      }
    }
    ```

### Step 2: Run the Production Build
Execute the production build script. This will create the distributable `.zip` file.
```bash
npm run build:prod
```
This command will:
1.  Set `NODE_ENV=production`.
2.  Merge `config/common.json` and `config/production.json` to create `dist/manifest.json`.
3.  Copy all files from `src/` into the `dist/` directory.
4.  Create a production-ready `.zip` file named `labsaver-vX.Y.Z-production.zip` in the root directory.

## 4. Chrome Web Store Submission

### Step 1: Navigate to the Developer Dashboard
Go to the [Chrome Web Store Developer Dashboard](https://chrome.google.com/webstore/developer/dashboard).

### Step 2: Upload the New Version
1.  Select the **LabSaver** item in your dashboard.
2.  Go to the **"Package"** tab.
3.  Click **"Upload new package"**.
4.  Choose the `labsaver-vX.Y.Z-production.zip` file that was generated by the build process.

### Step 3: Update Store Listing (If Necessary)
1.  Go to the **"Store listing"** tab.
2.  Update the description, screenshots, or any other metadata if changes in this release require it.

### Step 4: Submit for Review
1.  Once the upload is complete and the store listing is updated, you will see a **"Submit for review"** button.
2.  Click the button to submit the new version to Google for review. The review process can take anywhere from a few hours to several days.

## 5. Post-Release Steps

After the new version has been submitted for review, complete the release process with these steps.

### Step 1: Create a Git Tag
Create a Git tag for the version you just released. This provides a permanent reference point to the exact state of the code for that release.
```bash
git tag -a v2.0.4 -m "Release version 2.0.4"
git push origin v2.0.4
```

### Step 2: Merge to `main` (if not already)
If you were working on a release branch, merge it back into `main`.
```bash
git checkout main
git merge release/v2.0.4
git push origin main
```

### Step 3: Monitor the Release
Keep an eye on the Chrome Web Store Developer Dashboard for the status of the review. Once the review is approved, the new version will be published automatically.

## 6. Rollback Procedures

If a critical bug is discovered after a release, a rollback may be necessary.

1.  **Unpublish the new version**: In the Developer Dashboard, you can unpublish the current version. This will prevent new users from installing it.
2.  **Re-submit a previous version**: You can re-upload a `.zip` file of a previous, stable version.
3.  **Hotfix Release**: The preferred method is to quickly fix the bug in a new branch, create a hotfix release (e.g., `v2.0.5`), and go through the release process again. This is generally faster than waiting for a rollback to be approved.

## 7. Release Verification

Once the new version is live on the Chrome Web Store:
1.  Install the extension on a clean Chrome profile directly from the store.
2.  Perform a final round of manual testing to ensure that the published version is working as expected.

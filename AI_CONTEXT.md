# AI Assistant Guide for the LabSaver Codebase

## 1. Purpose of This Document

This document provides essential context and strict rules for AI assistants working on the LabSaver Chrome extension codebase. Its purpose is to prevent regressions, ensure security, and guide you to make safe, effective, and architecturally consistent changes. **Read and adhere to these rules before making any modifications.**

## 2. Historical Context: The Version 2.0.3 Regression

A critical regression occurred in version 2.0.3 because of a manual, error-prone build process. The codebase was split into two directories, and the `package-extension.sh` script failed to include essential files in the final build. This caused the extension to be published in a broken state.

The subsequent architecture refactor (Phase 1 & 2) consolidated the codebase into a single `src/` directory and introduced an automated, environment-aware build system ([`scripts/build.js`](scripts/build.js)). This history is the primary reason for the strict rules below. **Your main directive is to avoid repeating this mistake.**

## 3. Critical Rules: What You Must Never Do

Violating these rules can lead to broken builds, security vulnerabilities, or loss of work.

- **NEVER Commit `config/production.json`**: This file contains production OAuth credentials and is explicitly ignored by Git. Never try to add it to the repository. The build system is designed to work without it in a development environment.

- **ALWAYS Use npm Scripts for Builds**: Never run the build process manually. Always use the provided npm scripts, as they set the critical `NODE_ENV` variable.
  - For development: `npm run build:dev`
  - For production: `npm run build:prod`

- **NEVER Manually Edit `manifest.json`**: The `manifest.json` file in the root directory is a template (`config/common.json`). The actual `dist/manifest.json` is generated by the build script ([`scripts/build.js`](scripts/build.js)). To change the manifest, you must edit the files in the `config/` directory.

- **ALWAYS Use `git mv` for File Moves**: If you need to move or rename a file, always use `git mv`. This is crucial for maintaining file history, which is important for understanding the evolution of the codebase. A simple `mv` command can be interpreted by Git as a deletion and a creation, which obscures the file's history.

- **NEVER Mix Dev/Prod OAuth Credentials**: The build system is designed to handle this automatically. The development OAuth client ID is in [`config/development.json`](config/development.json), and the production ID is in the untracked `config/production.json`. Do not copy credentials between these files or hardcode them anywhere else.
  - **Development** ("Lab Saver" project): `699618980300-c7jn8t9kccdfm00c0704a29mduovqpe4.apps.googleusercontent.com`
  - **Production** ("LabSaver Production" project): `609855124330-qhqklvllcvmft7v8f9k42csfqupu1p6d.apps.googleusercontent.com`

## 4. Directory Structure Rationale

Understanding *why* the directories are structured this way is key to making correct changes.

- **`src/`**: This is the single source of truth for the extension. **Everything in this directory gets packaged into the final extension.** If a file needs to be accessible at runtime (like an icon or a data file), it *must* be in `src/`.
- **`config/`**: This directory is exclusively for configuring the `manifest.json` file for different environments. It allows for a clean separation between base settings and environment-specific overrides (like OAuth keys).
- **`scripts/`**: These are developer tools. They are meant to be run from the command line to build the project or manage data. **Files in this directory are never included in the final extension package.**
- **`tests/`**: Contains automated tests. Like `scripts/`, these are for development and are not part of the final product.
- **`dist/`**: This is the build output directory. **Never edit files in `dist/` directly**, as they will be overwritten by the next build.

## 5. Common Pitfalls and How to Avoid Them

- **Pitfall**: Adding a new icon or data file but the extension can't find it.
  - **Reason**: You likely added the file to a top-level directory like `images/` instead of `src/images/`.
  - **Solution**: Always place runtime assets inside the `src/` directory.

- **Pitfall**: Changing the extension's name in `package.json` and expecting it to update in the extension.
  - **Reason**: The extension's name is controlled by the `manifest.json`, which is generated from `config/common.json`.
  - **Solution**: Edit the `name` field in [`config/common.json`](config/common.json).

- **Pitfall**: The production build fails due to a missing file.
  - **Reason**: The `config/production.json` file is missing, which is expected in a standard development environment. Production builds should only be run in a secure, designated release environment.
  - **Solution**: Use `npm run build:dev` for all development work. Do not attempt to create a `config/production.json` file.

## 6. Testing Requirements

Before finalizing any changes, you must ensure that the core functionality remains intact.

- **Run LOINC Derivation Tests**: The LOINC derivation logic is a critical part of the extension. Run the tests to ensure you haven't introduced any regressions.
  - Command: `npm test`
- **Perform a Build Test**: Always run a development build after making changes to ensure that the build process completes successfully.
  - Command: `npm run build:dev`
- **Manual Verification**: After building, load the unpacked extension from the `dist/` directory into Chrome and perform a manual test of the export functionality on both Function Health and Sutter Health.

## 7. Architecture Decision Records (ADRs)

These are key decisions that have shaped the current architecture. Understanding them will help you make consistent choices.

- **ADR-001: Choice of a simple Node.js build script over a bundler.**
  - **Decision**: Use a plain Node.js script for the build process.
  - **Rationale**: The extension's build needs are simple (merge JSON, copy files, zip). A full-featured bundler like Webpack or Vite would add unnecessary complexity, configuration overhead, and dependencies. The current script is transparent and easy to debug.

- **ADR-002: Consolidation of all source code into `src/`.**
  - **Decision**: All files to be included in the final extension package must reside in the `src/` directory.
  - **Rationale**: This creates a single source of truth and eliminates the ambiguity of the previous dual-directory structure. It simplifies the build script's logic to "copy everything from `src/`," which is robust and easy to understand.

- **ADR-003: Environment-specific configuration via JSON merging.**
  - **Decision**: The `manifest.json` is generated by merging a base config with an environment-specific config.
  - **Rationale**: This is a clean, declarative way to manage differences between environments. It avoids conditional logic within the source code and keeps sensitive information (like production OAuth keys) separate from the main codebase.
